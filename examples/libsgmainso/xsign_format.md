# x-sign 载荷结构（实测反推，仅 SG 6.8.260602 / 千问 7.3.6.3039）

**x-sign 的 76 字节载荷里没有请求内容。**

| | 观测值 |
|---|---|
| 长度 | 76 字节 |
| 编码 | 标准 Base64（含 `+/`） |
| 外层掩码 | 2 字节交替：`偶数位 ^ b[74]`，`奇数位 ^ b[75]` |
| 头部 8 字节 | `6b 36 4c 82 7d 34 e7 10` |
| 同参重复调用 | 每次不同（随机量 + 计数器） |
| `x-umt` | 同进程内恒定 |

证据：`test_vectors.json` 的 `diff_vectors`（6 组同参 + 23 组单字段差分）
与 `fixed_vectors`（30 组完全同参）。

## 1. 归一化后的字段布局

掩码剥除后（`n[i] = b[i] ^ b[74 + (i & 1)]`）：

```text
偏移   长度  内容                                  观测（6.8，30 次同参）
0      8     6b 36 4c 82 7d 34 e7 10               常量；env=2 时前 4 字节与第 6 字节改变
8      1     00                                     常量
9      1     每调用变化（0xa0..0xaf 量级）            随机/序号片段
10     1     00                                     常量
11     11    每调用全变                              随机量（见 §4）
22     4     00 00 01 83                            常量（387，疑似长度/计数字段）
26     44    设备/会话常量块                          跨全部请求字段恒定
70     6     每次调用递增的计数器                      68..75 区域
```

## 2. 关键否定结论：请求内容不进入 x-sign

6.8 上做了**单进程内单字段差分**（6 次同参 + 23 次只改一个字段）：

| 变化的字段 | x-sign 76 字节中发生变化的偏移 |
|---|---|
| `requestId` | 无（除随机区 9, 11..21） |
| `api`（两个不同值） | 无 |
| `t` | 无 |
| `data` 的 md5（3 个不同值） | 无 |
| `v` | 无 |
| `utdid` / `uid` / `sid` / `ttid` / `deviceId` | 无 |
| `x-features` / `extdata` | 无 |
| `useWua`（true→false） | 无 |
| `extendParas` / `bizId` / `flag` / `authCode` | 无 |
| `env`（0→1→2） | 头部 1..4,6 与 32..56 |
| `miniWua` 输入 | 67 |
| `signKey` 输入 | 抛 `SecException`（native 侧校验） |
| `appKey` 未注册 | 抛 `SecException`（native 侧查表） |

也就是说：**除 `env` 与 `miniWua` 外，70102 产出的 x-sign 与 12 个入参全部无关。**
26..69 这 44 字节是设备/会话级常量，跨请求、跨输入保持不变。

同参 30 次连续调用中，**76 字节里有 60 个偏移恒定**，只有 9、11..21（随机）和
68..75（计数器）在变。

## 3. 计数器

- 68..75 区域随调用递增，步长在 30 次同参调用中稳定。
- 在 6.6 上曾更清晰地量到 `[72..73]` 为大端 16 位计数器、每次 +0x10；
  6.8 的对应区域（68..75）步长稳定但未被单独标定。6.6 的数据已删除，需要时可重采。
- 初值每进程不同（观测到 `0x0010` 与 `0xe8e3`），即被随机/时间播种。
- 是否被其它 SG 命令共享推进：**未验证**。

## 4. 尚未排除的可能性（关键）

偏移 11..21 的 **11 字节**每调用全变。存在两种解释，黑盒无法区分：

1. 它就是纯随机数（不含请求信息）→ x-sign 完全与请求无关，请求绑定由别的机制承担
   （cookie / `_m_h5_tk` / 其它参数）。
2. 它是 `MAC(请求)[:11] ^ 随机掩码` → 这正是「x-sign 是请求的 hash」的形态，
   但随机掩码让黑盒观测不到任何相关性。

**判定必须下沉到 native**：找到填充这 11 字节的函数，看它是否读入请求缓冲。
这是下一步唯一有决定性的动作（见 `known_offsets.json` 的 `open_questions`）。

## 5. 其它已确认行为

- `useWua=false` → 返回 map 无 `wua` 键。
- `env=1/2` → `x-umt` 改变，`x-sign` 头部与 32..56 区域改变。
- 6.8 的 `x-sgext` 解码后出现明文自测载荷，例如
  `MyProcessor^offset^length` 与重复的 `MySecurityKeyLow`，
  提示该字段内部是 `offset/length` 三元组结构，值得单独分析。
- 千问 7.3.6 的 `ISGPluginManager` 变成动态代理，没有可反射的 `IRouterComponent`
  字段；取 router 需改为枚举 classloader 找 DexPathList 含 `libsgmain.so` 的那个
  （见 `fr_session.py` + `diff_probe.js`）。

## 5. 编码层已完全确定（135 组向量逐字节验证）

`xsign_codec.py` 是本节结论的可执行参考实现，`--selftest` 对全部 135 组向量
（`oracle_vectors` 76 + `diff_vectors` 29 + `fixed_vectors` 30）做
`decode -> encode` 往返：

```
向量 135, decode->encode 载荷逐字节还原 135
```

- **外层编码**：标准 Base64 字母表（含 `+` / `/`，**不是** base64url），解码固定 **76 字节**。
- **外层掩码**：2 字节交替，`n[i] = b[i] ^ b[74 + (i & 1)]`，仅对 `i >= 10`；
  掩码字节就是载荷自己的最后两字节。归一化后 `b[74:76] == 0`。
- **字符串层面的唯一差异**：最后一个 base64 字符的低 4 位是编码器未清零的丢弃位，
  **不属于签名内容**（135 组里只有 4 组恰好为 0）。因此一致性判据是载荷 76 字节，
  不是字符串。

### 字段布局（对 30 次同参连续调用实测）

| 偏移 | 长度 | 名称 | 同参调用内 |
|---|---|---|---|
| 0 | 8 | header | 恒定（`6b364c827d34e710`；env=2 时前 4 字节与第 6 字节改变） |
| 8 | 1 | pad8 | 恒为 0x00 |
| 9 | 1 | a | 每调用变化 |
| 10 | 1 | pad10 | 恒为 0x00 |
| 11 | 11 | nonce | 每调用全变 |
| 22 | 4 | len_field | 恒为 `00000183` = 387（语义未确定） |
| 26 | 44 | device_blob | **按会话恒定**（跨调用、跨全部入参） |
| 70 | 2 | tail_a | 每调用变化（来源未定） |
| 72 | 2 | counter | 大端 16 位，每次 70102 调用 **+0x10** |
| 74 | 2 | mask | 掩码自身 |

### 会话相关性（重要更正）
`device_blob` **不是设备级全局常量，而是按进程/会话恒定**：本次 76 组向量跨 4 个以上
app 进程采集，得到 4 种不同的 blob；同一进程内无论怎么改入参都只有 1 种。
6.8 的 blob 内**不再包含** `x-umt`（6.6 时包含，偏移探测为 -1）。

### 输入依赖最终判定
对 12 个入参逐字段做单字段差分（`oracle_vectors` + `diff_vectors`），
`device_blob` 与 `counter` 的取值只随**进程**变化，**与所有入参无关**；
仅 `env` 会改变 header 与部分载荷字节。结论与前一轮一致，并已在 135 组向量上复核。

## 6. 仍未知（不猜测）
1. `nonce`（11 字节）的生成过程。
2. `device_blob`（44 字节）的生成过程与其绑定的会话材料。
3. `counter` 初值的播种源（观测到同进程内固定、跨进程不同）。
4. `a` / `tail_a` 两个每调用变化字节的来源。
5. 76 字节载荷的**生产**循环。已定位的是**字符串常量解码器**
   `sub_54b70`（0x54b70，公式 `dst[i] = src2[i] ^ (src1[i] - key)`，key=0x81，
   src 全部来自 .rodata），它解出的是输出键名与内部名 `avg_getSecurityFactors`，
   **不是**载荷本身。载荷生产循环仍未在 trace 中定位（`w1=0x4c` 的调用点未出现）。

因此：当前阶段可以**精确解析与复现**设备产出的 x-sign（含载荷级一致），
但**无法离线生成**一个全新的、服务器会接受的新 x-sign —— 缺的是 nonce/blob/counter
的生成算法，那需要 native 生产者逻辑或设备会话密钥。
